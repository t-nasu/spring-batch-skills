# 0003 chunk の Reader の作り方は開発者が選ぶ

## 問い

大量件数の chunk 処理で、Reader がリポジトリを経由せず Mapper を直接使うことを許すか。

## 許す場合

利点
- カーソル読み（`MyBatisCursorItemReader`）で、件数が増えてもメモリ使用量が一定で、速い
- MyBatis 公式の Reader が持つ再起動時の読み取り位置の保存を、そのまま使える
- 書くコードが少ない

欠点
- 読み取りの経路がリポジトリと Reader の二つになる
- 「どのデータを処理対象とするか」という業務条件が SQL に埋もれ、domain から見えなくなる
- 一つ例外を作ると「ここも例外に」と広がりやすい

## 許さない場合

利点
- 層のルールに例外がない。読み取りが常に domain のリポジトリ経由で一貫する
- テストでリポジトリを差し替えやすい

欠点
- domain のリポジトリにページ単位で読むメソッドが要り、domain に「ページ」という技術的な概念が入る
- 再起動時の読み取り位置を自前で保存する Reader を書く必要がある
- OFFSET によるページングは件数が多いと遅く、処理中にデータが変わると取りこぼしや重複が起こりうる

## 決定

当初（2026-10-19）は「条件付きで許す」とした。その後、社内スキル `add-inbound-batch` に「バッチ処理から直接 Repository を呼ばない」という決まりがあり、Mapper を直接使う案はその趣旨と食い違うと分かった。

これは技術的な判断であり、ジョブごとに開発者が選ぶこととした。エージェントは設計図の段で二案を示し、承認のときに選んでもらう。Mapper を直接使う案を選んだ場合は、読み取り専用に限ること、DTO からドメインへの変換を Reader の中で行うこと、抽出条件の意味を Reader のクラスコメントに業務の言葉で書くことを課す。
